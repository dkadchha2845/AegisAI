AegisAI

An Agentic Digital Public Safety Platform for Autonomous Multi-Modal Fraud Investigation

Authors Dhrumil Kadchha · Smruthi Chandrashekar

Not a scam classifier — a digital investigator. Give it an email, an SMS, a WhatsApp screenshot, a QR code, a URL, a PDF, an APK, a recording, a phone number, a UPI ID, or a live call. A graph of specialised agents investigates it, correlates the findings against a persistent fraud-intelligence graph, scores the risk with a calibrated model, and explains why — with a source for every claim.

After five iterations of refusing to, this page can now write the sentence: an investigation flows through the API. Evidence is submitted over HTTP, routed by input type through the graph, executed with a parallel fan-out over eight agents in four tiers, traced, persisted, streamed back node by node as each one actually completes, reported as JSON or PDF, and erased on request — rows, stored bytes and progress journal together. Task 1.7 put the inherited engine inside that graph without changing a line of it, and the two paths now provably agree signal for signal: the same stage labels, the same manipulation map, the same fused drivers. One qualification remains, and it is 1.8's — the graph runs in the API process rather than on a worker, so a restart loses an in-flight run.

What changed, and what didn't

AegisAI is not greenfield. It inherits a working, tested scam-call engine built for the ET AI Hackathon 2026 and widens it into an investigation platform. The pivot is breadth and architecture — never a restart.

07 — Research

Four contributions, not ten

Multi-agent fraud detection is not novel, and claiming it is would be the fastest route to a desk reject. These four are defensible with experiments.

C1

Conversational-arc detection

Fraud modelled as a staged psychological process across calls, chats and threads — not an artefact classified in isolation.

C2

Measured agent disagreement

Typed results with calibrated confidence, and disagreement between scoring paths reported rather than hidden.

C3

The AIFC corpus

Multimodal, multilingual Indian fraud evidence with a deliberately hard benign class and published annotator agreement.

C4

False-positive-first evaluation

Showing that several choices which improve accuracy make FPR worse — the binding constraint for citizen-facing safety systems.

08 — Definition of done

Four gates, then the running application

A task is not done because the code exists. One task at a time, verified, before the next.

make gates   # the canonical command: tests, contract, typecheck, build
make check   # the gates plus ruff and mypy
— then start the stack, run the real path, and read the browser console.
The docs no longer name a test count. A test forbids it: the suite grows
with every task, and a number written into prose is stale on arrival.

Standing invariants

  • ✓schema/ is the single source of truth — Pydantic and TypeScript change together
  • ✓The frontend is a pure renderer — no scoring maths in React
  • ✓Degradation is explicit — every path has a fallback that still answers
  • ✓False positives are a first-class failure — every agent ships a benign test
  • ✓The LLM explains, extracts and ranks. It never scores.
  • ✓No claim without a measurement
  • ✓Evidence is data, never instructions

Security, non-negotiable

  • !SSRF — the URL agent fetches attacker-supplied URLs. Block private ranges and cloud metadata, re-resolve DNS after every redirect.
  • !Malware — APKs are analysed statically in a network-less container. Never executed.
  • !Consent — live audio requires an explicit gate and a visible indicator. Never designed around covert recording.
  • !Tenancy — org isolation enforced in the repository layer, not the route.
Next action

Task 1.8 — Async job system

Eight agents now run inside the graph, and every one of them runs in the process that serves the request. That is fine for a classifier that answers in 30 ms and wrong for an APK scan that takes two minutes: ARCHITECTURE.md §2 already budgets 120 s for static analysis and says it never runs in-request. 1.8 is the worker that makes that true — Redis and Celery, queues split by cost class (fast, slow, sandbox), results landing back in the evidence store, and a dead-letter policy for what never finishes.

It also closes the honest gap 1.6 wrote down rather than hid. Today a restart loses every in-flight investigation and its durable row says QUEUED for ever, because the runner and its progress journal live in memory. The acceptance criteria are the ones that make the difference checkable: a 90-second stub runs off the request path, the API returns in under a second with an investigation that later completes, and a worker crash loses no work — which is where the LangGraph checkpointer stops being in-process, and where "resume after a crash" stops meaning "resume unless the crash took the process".
